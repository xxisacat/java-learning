## 这批题的由来

泛型是**集合的地基** —— 下周的 `ArrayList<String>`、`HashSet<Player>`、`HashMap<Integer, Item>` 全靠它。你今天写的 `Backpack<T>`，就是 `ArrayList<E>` 的小号替身。

游戏代码里泛型基本就两个形状，两题各练一个：

- **通用容器** —— 装什么由调用方决定（背包 / 仓库 / 对象池 / 缓存）→ 题 A
- **通用规则** —— 规则和数据类型解耦（筛选 / 排序 / 匹配）→ 题 B

## 二、编程题 A：通用背包（泛型类 + 泛型方法）

包：`src/genericity/loot/`

**场景**：背包「装什么」不该写死 —— 装武器的背包、装材料的背包、以后装玩家的背包，是同一个类。这就是泛型类存在的理由。

### 1. 类 `Weapon`（普通小类）

- 字段：`name`（武器名）、`attack`（攻击力，`int`）
- 构造器 + getter 自己写。

### 2. 类 `Backpack<T>`（今天的主角）

| 方法 | 规格 |
|---|---|
| `Backpack(int capacity)` | 给定容量 |
| `boolean add(T item)` | 装一件。装得下 → 装入并返回 `true`；**满了 → 返回 `false` 且一件都不装** |
| `T get(int index)` | 取第 index 件（从 0 开始）。题目约定下标一定合法，不做越界检查 |
| `T removeLast()` | 取走最后装入的那件，size 减 1。约定只在非空时调用 |
| `int size()` | 当前件数 |
| `boolean isFull()` | 是否已满 |
| `int capacity()` | 总容量 |

- 内部**用数组存**（先别用 ArrayList —— 集合下周才学，这题的正题就在数组上）。
- 数组怎么创建你自己决定。**你大概率会撞到一个编译错误** —— 把 javac 报错原文贴我，然后想办法绕过去。
- 提示：如果你看到编译器说「使用了未经检查或不安全的操作」—— 那是这题躲不掉的，**先放着别管**，批改时讲。

### 3. 类 `LootUtil`（泛型方法）

```java
public static <T> int transfer(Backpack<T> from, Backpack<T> to)
```

- 把 from 里的装备**搬**进 to，直到 from 空或者 to 满。
- 返回**实际搬运的件数**（老规矩：改状态的方法，要把真实结果交回调用方）。
- 搬走的从 from 消失；装不下的留在 from（哪几件留下不作要求，件数对上就行）。

### 4. `Test.main` 验收

跑出来长这样（**数字必须对得上**，措辞可以有小的出入）：

## 三、编程题 B：战利品筛选（泛型接口 + 通配符）

包：`src/genericity/filter/`

**场景**：筛选规则不该跟数据类型绑死 ——「价格 ≥ 100」这一条规则，既要能筛 `Backpack<Item>`，也要能筛 `Backpack<Weapon>`。这就是泛型接口 + 通配符的用武之地。

### 1. 物品三兄弟

- `Item`：`name`、`price`（`int`）—— 普通类
- `Weapon extends Item`：多一个 `attack`（`int`）
- `Gem extends Item`：多一个 `color`（`String`）
- 字段 + 构造器 + getter 自己写。

### 2. 接口 `LootFilter<T>`（泛型接口）

```java
public interface LootFilter<T> {
    boolean test(T item);
}
```

### 3. 类 `FilterUtil` —— 两个方法签名**照抄，一个字都别改**（这是今天的设计题答案，批改时会问你为什么）

```java
public static <T> Backpack<T> filter(Backpack<T> bag, LootFilter<? super T> rule)
```

- 返回一个**新背包**（容量 = 原背包的 size），把 `rule.test(...)` 为 true 的原样装进去；原背包不动。

```java
public static int totalPrice(Backpack<? extends Item> bag)
```

- 把所有物品的价格加起来返回。

- 碰撞任务：在 `totalPrice` 里**故意**加一行，往 bag 里 `add` 一把武器 → 贴 javac 报错原文 → 删掉。想想它和 `filter` 里 `? super` 的差别（概念题 Q5 就在这）。
-（好奇的话可加做）把 `? super` 删掉再编译一次 —— Test 里「筛武器背包」那行会编不过，贴原文，再加回来。

### 4. `Test.main` 验收

```
=== 题 B：战利品筛选 ===
战利品 3 件，总价 410
武器背包 2 件，总价 210
按价格 ≥ 100 筛战利品：2 件，总价 350
按价格 ≥ 100 筛武器背包：1 件，第一件：巨锤
```

数据自己摆：

- `Backpack<Item> loot`（容量 3）：短剑（60，攻 10）→ 红宝石（200，红）→ 巨锤（150，攻 35）

  —— 「筛武器背包」那一行能编过，就是 `? super T` 存在的全部理由。为什么？批改时问你。

| Q6 | 泛型类里 `static T make(){ return null; }` | `error: non-static type variable T cannot be referenced from a static context` |
| Q6·变体 | 方法体碰实例：`return this.items[0];` | `error: non-static variable this cannot be referenced from a static context` |

【要背】B① 里的 `capture` = "某个具体的、但编译器不告诉你是哪个的 Item 子类型"。就靠这个"保密"，`? extends` 只能读不能写。（对照：`? super` 的机器可以往里**喂** —— 一读一写，方向相反。）

【要背】B② = 泛型不变性的第二现场（第一现场是「加验」那条），这次报错措辞升级了：`inference variable T has incompatible equality constraints Item,Weapon` —— 编译器按两边要求各推了一遍 T：赋值目标 `Backpack<Item>` 要 T=Item，实参 `Backpack<Weapon>` 要 T=Weapon，一个 T 分不了身，就在**调用点**报推断失败。解药：左右各自报各自的名（`Backpack<Item>` 接 loot、`Backpack<Weapon>` 接 weapon），T 就安了。

【了解】拿「宽类型」接住是合法岔路（本机实测能编过）：`Backpack<? extends Item> x = FilterUtil.filter(weapon, rule);` —— 接住后 `size()/get()/totalPrice()` 照用（`totalPrice` 签名收的就是 `Backpack<? extends Item>`），但接住后不能往里写。读多写少可用，本题整改用不到。

【要背】Q6 的正确姿势：static 方法**不能蹭类的类型参数 T**（T 跟着实例走，static 没有实例）；但**自带 T 就合法** —— `public static <T> T make()` 干净版本机实测**编过**，写法与 `LootUtil.transfer` 同款。报错翻译：类的 T = 每个实例随身的「这包装什么」账本；static 想用 T 就得「去 `Backpack.this` 那本账取」，没有 this → 报错。

### 今晚的最小记忆集【要背】

1. 构造器 = **类名 + 括号，没有返回类型**（`void` 也不行）
2. `new T[n]` 不行；标准绕法 `(T[]) new Object[n]`（那句 unchecked 警告属正常，先不管）
3. 泛型类型之间**没有父子关系**：`LootFilter<Item>` ≠ `LootFilter<Weapon>` —— 哪怕 Item 是 Weapon 的爹
4. 通配符 = 接收方的放宽开关：`? extends X` 往外拿（能读不能写）；`? super X` 往里喂（能写不能读）
5. 接口只给形状；准则由**实现的人**填（匿名内部类 = 只写一次的准则）
6. **一次计算，存变量，用多次** —— 同一个结果连算两遍属于「重复干活」，现在对不代表以后对（有副作用时就是两个答案）
